# CLAUDE.md

Guidance for AI agents working in this repo. See [README.md](README.md) for the
user-facing overview and [docs/MARAUDER_PROTOCOL.md](docs/MARAUDER_PROTOCOL.md)
for the serial interface the app drives.

## What this is

**Wavehound** is WiFi fox-hunting for the Flipper Zero WiFi dev board. It locates
a 2.4 GHz transmitter by its per-frame RSSI. It is **receive-only**.

Wavehound is a **Flipper external app** (`.fap`) only. The dev board runs **stock
[ESP32 Marauder](https://github.com/justcallmekoko/ESP32Marauder) firmware
v1.19.0** (the `MARAUDER_FLIPPER` build); the app is a UART client that drives
Marauder's serial CLI and renders the results. There is no custom board firmware
in this repo — the earlier `firmware/` directory (Wavehound's own ESP-IDF
project) was removed when the app was converted to target Marauder.

Built with `ufbt`, Flipper firmware SDK (API 88.2, FW 1.5.1).

## Layout

```
flipper_app/
  application.fam         app manifest (appid, fap_version, assets)
  wavehound.c             entry, board power/expansion, UART line dispatch
  wh_marauder.c / .h      Marauder command builders + serial line parsers
  wavehound_i.h           WavehoundApp struct, WhTarget/WhSavedMac, view & event enums
  wh_uart.c               USART worker, line splitting, keep-alive poll
  wh_store.c              saved MACs: load/add/update/delete on SD
  wh_settings.c           app settings: load/save on SD (settings.txt)
  wh_oui.c                vendor lookup from SD oui.db (binary search, no RAM load)
  scenes/                 one file per screen (scene-manager pattern)
  views/wh_hunt_view.c    hunt screen + geiger click thread
  assets/oui.db           bundled vendor db, generated by build_app.py
tools/gen_oui.py          build oui.db from Wireshark's manuf
build_app.py              generate+bundle oui.db, then run ufbt
docs/MARAUDER_PROTOCOL.md the subset of Marauder's serial CLI the app uses
```

## Scene pattern (flipper_app)

Scenes are registered in `scenes/wh_scene_config.h` via the `ADD_SCENE(prefix,
name, id)` X-macro. Adding a scene means: add one `ADD_SCENE` line there, create
`scenes/wh_scene_<name>.c` with `wavehound_scene_<name>_{on_enter,on_event,on_exit}`,
and (usually) a new `WhCustomEvent` / `WhViewId` in `wavehound_i.h`. Shared app
state lives in `WavehoundApp` (`wavehound_i.h`); the UART worker writes results
under `results_mutex`.

## Protocol is contract

The app talks to Marauder over a plain-text, line-based CLI. The command
builders and the reply-line parsers both live in `wh_marauder.c`; the UART
worker in `wavehound.c` dispatches each received line by `app->board_mode`
(`WhBoardScanning`/`Hunting`/`Info`). The exact subset — every command sent and
every reply line shape parsed — is documented in
[docs/MARAUDER_PROTOCOL.md](docs/MARAUDER_PROTOCOL.md). Any change to a command
or to a parsed line shape must stay consistent across **all three**:
`wh_marauder.c`, `wavehound.c`, and the doc. Update the doc in the same change.

Key Marauder facts the app depends on (see the doc for detail):

- Fox-hunt targets are addressed by **list index**, not MAC. The app scans with
  `scanall`, assigns each AP an index in print order, resolves each station's AP
  by MAC, and hunts with `foxhunt -w <ap>` / `foxhunt -s <ap> <sta>`. A typed or
  saved MAC is injected with `add -a` first, then hunted by the returned index.
- `clearlist -a` resets the board's lists (and indices) before a **fresh** scan;
  a resume keeps them so stored indices stay valid.
- Marauder's `"> "` prompt has no trailing newline and prefixes the next line;
  `wh_on_line` strips a leading `"> "` before parsing.

## Building

```bash
python3 build_app.py          # regen oui.db + ufbt build (needs ufbt on PATH)
python3 build_app.py --launch # build, upload and run on a connected Flipper
cd flipper_app && ufbt        # app only, skip the db step
```

Don't assume `ufbt` is installed in this environment — it usually is not. Prefer
reasoning about the code and keeping changes buildable; only invoke the toolchain
when the user asks or it's clearly available. The parsers in `wh_marauder.c` are
plain C and can be exercised on the host with a small harness.

## Conventions

- Both sides ignore lines they don't understand (Marauder boot chatter is
  harmless). Marauder's replies are free text, one message per `\n` line.
- App symbols: `wh_`/`Wh` prefix. Marauder helpers are `wh_marauder_*`.
- Match the existing comment density and naming of the file you're editing.

## Versioning (agents may bump)

An agent may, **when it judges the change justifies it**, increase the app
version: `fap_version` in
[flipper_app/application.fam](flipper_app/application.fam). A user-visible or
protocol-affecting change warrants a bump; a pure refactor or doc tweak usually
does not. There is no longer a separate board-firmware version (the board runs
Marauder).

### Tagging a release

Releases carry a **single git tag `v<fap_version>`** (e.g. `v2.0`). Work normally
lands on `main` as a **squash-merged PR**, so the release commit's SHA only
exists once the PR is merged. The flow after a merge is:

1. Set the catalog `commit_sha` (see below) and commit that to `main`.
2. Tag the **squash-merge commit** (the one carrying the new `fap_version`) as
   `v<fap_version>` and push the tag. Existing tags point at their PR's
   squash-merge commit — match that. If a bump lands as a direct commit on `main`
   rather than via a PR, tag that bump commit and point `commit_sha` at it.

## Catalog metadata

The [Flipper Apps Catalog](https://github.com/flipperdevices/flipper-application-catalog)
submission files live in `flipper_app/catalog/`: `manifest.yml`, `changelog.md`
and `screenshots/`.

**Keep `manifest.yml` and `changelog.md` in sync** — with each other and with
[flipper_app/application.fam](flipper_app/application.fam):

- Every app version bump (`fap_version`) gets a new top entry in `changelog.md`
  (newest first), and the catalog version is driven by `fap_version`.
- `manifest.yml` leans on `application.fam` for the shared fields (name, id,
  category, version, author, icon, short_description) — don't duplicate them. If
  one of those changes in the `.fam`, there's nothing to change in the manifest,
  but do check they still agree.
- The manifest's `changelog` and `screenshots` paths must point at files that
  exist.
- `commit_sha` must point at the commit on `main` that actually carries the
  submitted code — i.e. the **squash-merge commit** of the release PR (the same
  commit the `v<version>` tag is on). That SHA doesn't exist until the PR merges,
  so the normal flow is: merge the PR, then make a small follow-up commit on
  `main` that sets `commit_sha` to the merge commit. That follow-up commit is
  **not** itself the referenced/tagged commit.

Path gotcha: the catalog bundler resolves the manifest's `@file` and screenshot
paths relative to `sourcecode.subdir` (`flipper_app`), **not** to the manifest's
own folder — hence the `catalog/` prefix on those paths.
